# celso

高速な日本語誤字脱字チェッカーの試作。

**修正候補を作り、単語 n-gram 言語モデルで編集前後を比べる**という古典的な手法を、
法令文向けにいくつか工夫して組み合わせている。GPU も深層モデルも使わず、
横浜市市税条例（約 20 万字）全体を 8 コアで約 1.3〜3 秒で検査できる。

```
$ echo "西口側までは宿泊から施設や地元の日本酒や、山の幸を揃えた飲食は店、呑み屋など多くあろう" | celso check
3..5    delete      「まで」→「」      Δ=4.35  西口側[まで]は宿泊から施設や地元の日
8..10   delete      「から」→「」      Δ=6.92  西口側までは宿泊[から]施設や地元の日本酒や、山
30..31  delete      「は」→「」        Δ=6.62  酒や、山の幸を揃えた飲食[は]店、呑み屋など多くあろう
40..43  inflection  「あろう」→「ある」 Δ=5.16  飲食は店、呑み屋など多く[あろう]
4 findings, 44 chars in 13.13ms
```

## なぜこの方式か

例文の誤り（宿泊**から**施設、飲食**は**店、多く**あろう**）は、どれも**単語としては正しく、並び方だけがおかしい**。

- 形態素解析の辞書では「宿泊/から/施設」がすべて既知語として解析できてしまうため、検出できない。
- ruri のような文埋め込みモデルは、文全体の意味をベクトルにまとめる。助詞が 1 つ増えても意味はほとんど変わらないので、埋め込みもほぼ動かない。

並びの不自然さを見るには言語モデルが必要になる。ただし、文全体の尤度をそのまま閾値で切ると、珍しいが正しい文まで拾ってしまう。
そこで「この位置をこう直すと尤度がこれだけ上がる」という**相対比較**で判定する。

## 仕組み

1. **分かち書き**: lindera + IPADIC。数字列は `<num>` にまとめる。全角英数は文字数を変えない NFKC で正規化する。
2. **候補生成**（[src/checker.rs](src/checker.rs)）
   | 種類 | 例 | 内容 |
   |---|---|---|
   | delete | 宿泊**から**施設 → 宿泊施設 | 単純な助詞・1 文字の平仮名・重複語を削る |
   | substitute | 西口側**まで**は → 西口側**に**は | 単純な助詞どうしを置き換える |
   | inflection | 多く**あろう** → 多く**ある** | 活用語と後続の助動詞列を、同じ語の別の活用形に置き換える（活用表はコーパスから収集） |
   | insert | 市税**□**賦課 → 市税**の**賦課 | 名詞の直後に助詞を補う |
   | homophone | 対**象** → 対**照** | 読みが同じで漢字の違う語に置き換える（かな→漢字や送り仮名違いは表記ゆれなので除外） |
   | char（既定は無効） | きかっけ → きっかけ | 1 文字削除・入れ替え・かな補完を、分かち書きし直して比較する |
3. **採点**: 編集箇所とその後続 3 語の対数確率（log10）を、編集前後で比べて差 Δ を出す。種類ごとの閾値（既定は 3.0）を超えたものを指摘する。
4. **誤検出の抑制**（精度の大半はここで決まる）
   - **未出現ゲート**: 元の文の編集箇所まわりに、コーパスで一度も見ていない 3-gram がある場合だけ候補を評価する。正しい文どうしの言い換え（「期間が」⇔「期間の」）を拾わない。
   - **文書内の繰り返し**: 指摘箇所の前後 2 文字を含む文字列が、同じ文書に 2 回以上出てくる場合は指摘しない。誤字はたいてい 1 回限りだが、「個人の市民税」のような条例特有の言い回しは何十回も出てくる。
   - **重なりの解消**: 1 文字以内で隣り合う候補は、Δ が最大のものだけを残す（「飲食は店」の「は」削除と「店」削除は同じ誤りの別解）。
5. **言語モデル**（[src/lm.rs](src/lm.rs)）: 4-gram、補間 modified Kneser-Ney。自前実装で、全次数の n-gram を 1 枚のオープンアドレス法ハッシュ表に詰め、キーは 64bit の指紋で持つ。

## 結果

学習コーパス: e-Gov 法令 XML（全 9,003 法令の最新版、3.9 億字）と Wikipedia 日本語版の分割ダンプ 1 本目（4.5 億字）。
合計 1.8 億トークン、語彙 28.6 万、n-gram 4,854 万。モデルは 1.08GB、構築に 3〜12 分（M 系 Mac・メモリ 7〜9GB）。

### 横浜市市税条例（学習には含まない）

- **速度**: 206,121 字を **1.3〜3.0 秒**（8 スレッド、モデル読み込み 1.3〜2 秒は別）
- **誤りのない原文に対する誤検出**: 30 件（1 万字あたり 1.5 件）。
  うち 8 件は「付則」→「附則」で、法令用語としてはむしろ直すべき指摘。
- **人工誤り**（各 300 文に 1 箇所ずつ誤りを入れ、`celso eval`）

  | 誤りの種類 | 検出 | 正しく直せた |
  |---|---|---|
  | 余計な助詞（宿泊から施設） | 90.3% | 89.0% |
  | 助詞の取り違え | 71.0% | 50.0% |
  | 活用の誤り | 78.3% | 71.0% |
  | 助詞の脱落 | 44.3% | 32.3% |

### JWTD v2 test（京大 日本語Wikipedia入力誤りデータセット、実際の誤字 5,357 文）

  | カテゴリ | 件数 | 検出 | 正しく直せた |
  |---|---|---|---|
  | 衍字（insertion_a） | 1,085 | 61.3% | 54.6% |
  | 漢字誤変換（kanji-conversion_a） | 1,782 | 28.6% | 27.0% |
  | 脱字（deletion） | 1,023 | 27.7% | 14.4% |
  | 誤字（substitution） | 774 | 25.3% | 11.6% |
  | 全体 | 5,357 | 32.7% | 25.1% |

  訂正後の正しい文に対する誤検出は、1 文あたり 18.7% と多い。Wikipedia の 1 文だけを渡す評価なので文書内繰り返しの抑制が効かず、固有名詞も多いためである。
  評価文は学習コーパスから除いてある（`scripts/exclude_eval.py`）。

## 使い方

```bash
scripts/build_all.sh                                    # コーパス取得〜モデル構築 (約 1 時間)
cargo run --release -- check fixtures/yokohama_shizei_jorei.txt
cargo run --release -- eval --sweep --thresholds 0,0,0,0,inf,inf fixtures/yokohama_shizei_jorei.txt  # 閾値の掃引
cargo run --release -- eval-jwtd data/jwtd/test.jsonl
cargo test --release -- --include-ignored               # 例文の回帰テスト (モデルが必要)
```

閾値は `--thresholds delete,substitute,inflection,insert,homophone,char` の順で指定する（log10、`inf` で無効）。

## 既知の課題と次の一手

- **文字単位の誤り（脱字・誤字・転字）が弱い**: 編集のたびに分かち書きし直すので、1 文あたり約 26ms かかり遅い。
  文字 n-gram モデルを併用して、分かち書きせずに採点するのが本命。
- **助詞の取り違えは、正しく直せる率が 5 割**: どの助詞に直すかが文脈だけでは決めにくい。
  1 段目で指摘した箇所だけを小さな MLM（`modernbert-ja-30m` など。ruri-v3 のベースなので candle 基盤を流用できる）で採点し直すと、精度を上げつつ速度も保てる見込み。
- **分野差**: 条例特有の言い回しはまだ取りこぼす。全国の例規集を学習コーパスに足すのが最も効果的だと思われる（条例は著作権法 13 条により著作物ではない）。
- **モデルサイズ**: 1.08GB。確率を 8bit に量子化し、4-gram の足切りを強めれば、数百 MB まで縮められる見込み。
- **学習ベースへの移行**: JWTD の train（約 70 万ペア）と、本ツールの `synth`（人工誤り生成）を合わせて、トークン分類型の誤り検出器（GECToR 型）を学習する。
  非自己回帰なので 1 回の推論で全文を判定でき、速度を保ったまま上積みできる可能性がある（GEC-Info-ja 掲載の「非自己回帰モデルを用いた高速な日本語文法誤り訂正」と同じ方向性）。
