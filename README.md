# celso

高速・軽量な日本語誤字脱字チェッカーの試作。

**Playground: https://bokuweb.github.io/celso/** （ブラウザの中だけで動き、入力した文章はどこにも送信されない）

**修正候補を作り、単語 n-gram 言語モデルで編集前後を比べる**という古典的な手法を、法令文向けに工夫して組み合わせている。

| 項目 | 値 |
|---|---|
| 配布物 | 約 22.6MB（モデル 14.2MB、同音異字の共起 3.7MB、文法モデル 2.0MB、カタカナ語の表 1.8MB、誤字パターン 0.8MB、判定器 0.3MB、活用表・同音異字表 0.4MB） |
| 常駐メモリ（peak footprint） | 横浜市市税条例 全文の検査で 約 29MB（モデル・共起・文法モデルは mmap） |
| 検査時間（市税条例 約 20 万字） | CPU 時間 約 0.4 秒（判定器・文法モデル・パターンなしなら 0.23 秒）、8 コアで約 0.2〜0.3 秒。2 回目以降は文単位キャッシュで約 30ms |

> Elsa 向けの本実装は jlsi/elsa の `crates/typo-checker`（RFC0059）。このリポジトリはコーパス構築と評価用。

```
$ echo "西口側までは宿泊から施設や地元の日本酒や、山の幸を揃えた飲食は店、呑み屋など多くあろう" | celso check
3..5    delete      「まで」→「」      Δ=-1.01  西口側[まで]は宿泊から施設…      別案: 「まで」→「に」(-1.41)
8..10   delete      「から」→「」      Δ=1.09   西口側までは宿泊[から]施設…
30..31  delete      「は」→「」        Δ=2.30   …揃えた飲食[は]店、呑み屋…
40..43  inflection  「あろう」→「ある」 Δ=0.12   …呑み屋など多く[あろう]          別案: 「あろう」→「あり」(-0.35)
```

指摘ごとに第一案と、別案を最大 2 件まで出す。Δ は判定器の対数オッズ（種類ごとの閾値 -1.2〜0.5 を超えたものを指摘する）。

## なぜこの方式か

例文の誤り（宿泊**から**施設、飲食**は**店、多く**あろう**）は、どれも**単語としては正しく、並び方だけがおかしい**。

- 形態素解析の辞書では「宿泊/から/施設」がすべて既知語として解析できてしまうため、検出できない。
- ruri のような文埋め込みモデルは、文全体の意味をベクトルにまとめる。助詞が 1 つ増えても意味はほとんど変わらないので、埋め込みもほぼ動かない。

並びの不自然さを見るには言語モデルが必要になる。ただし、文全体の尤度をそのまま閾値で切ると、珍しいが正しい文まで拾ってしまう。
そこで「この位置をこう直すと尤度がこれだけ上がる」という**相対比較**で判定する。

## 仕組み

1. **分かち書き**: [delarocha](https://github.com/bokuweb/delarocha)（Zig コア）+ IPADIC。
   - 辞書は `celso build-dict` で一度だけバイナリに変換し、起動時に mmap する。
   - 語彙外の語は品詞クラス（`<名詞-固有名詞>`、`<動詞-自立-連用形>` など）にまとめる。
   - 数字列は `<num>` にまとめる。
2. **候補生成**（[src/checker.rs](src/checker.rs)）。閾値は Δ（log10）で、法令文 / 一般文の順。
   | 種類 | 例 | 内容 | 閾値 |
   |---|---|---|---|
   | delete | 宿泊**から**施設 → 宿泊施設 | 単純な助詞・機能語の平仮名 1 文字・重複語を削る | 4.0 / 4.5 |
   | substitute | 西口側**まで**は → 西口側**に**は | 単純な助詞どうしを置き換える | 4.5 / 5.5 |
   | inflection | 多く**あろう** → 多く**ある** | 活用語を同じ語の別の活用形に置き換える。落としてよい助動詞は推量の「う」「よう」だけ | 1.5 / 3.0 |
   | insert | 市税**□**賦課 → 市税**の**賦課 | 名詞の直後に助詞を補う | 3.5 / 4.0 |
   | homophone | 対**象** → 対**照** | 読みが同じで漢字の違う語に置き換える（表記ゆれは除く） | 4.0 / 4.5 |
3. **採点**: 編集箇所とその後続の語の対数確率を、編集前後で比べて差 Δ を出す。
4. **誤検出の抑制**
   - **未出現ゲート**: 編集箇所まわりに、モデルにない 3-gram がある場合だけ候補を評価する。
   - **文書内の繰り返し**: 指摘箇所の前後 2 文字を含む文字列が文書に 2 回以上出てくれば、意図した表記とみなす。
   - **箇所へのまとめ**: 1 文字以内で隣り合う候補は同じ誤りの別解とみなす。そのうえで、自分の種類の閾値を超えた案の最良を指摘し、閾値の 1.0 下までを別案に添える。
5. **文書種別ごとの閾値**: 契約書・法令文・一般文を自動判定する。
   - 契約書: 「甲」「乙」「本契約」「委託者」などの密度で判定する。
   - 法令文: 条・項・号の参照や法令用語の密度で判定する。
6. **言語モデル**（[src/lm.rs](src/lm.rs)）: 補間 modified Kneser-Ney を自前で実装した。

   | 項目 | 値 |
   |---|---|
   | 次数 | 3-gram |
   | 語彙 | 1 万語 + 同音異字の約 5 千語 + 品詞クラス |
   | 足切り | 2-gram は 5 回以上、3-gram は 10 回以上 |
   | 配布形式 | `CELSOLM4`: 1 枠 4 バイト（16bit 指紋・8bit 確率・8bit backoff）を mmap |

7. **文単位キャッシュ**（`Checker::with_cache`）: 文と文書種別のハッシュをキーに指摘を保持する。
8. **同音異字の共起モデル**（[src/cooc.rs](src/cooc.rs)）: 同音異字の組になる約 9 千語について、同じ文に出やすい語を「共起回数 × PMI」の大きい順に 128 語持つ（3.7MB、mmap）。手がかりの語は言語モデルの語彙とは別に、頻出 5 万語のうち漢字を含む約 3.4 万語から選ぶ。
   - 誤変換の候補には、n-gram の Δ に「文中の語との相性」の差を足す。
   - n-gram は前後 2 語しか見ないので、「衛生 / 衛星」のような違いはこちらで見る。
9. **判定器**（[src/rerank.rs](src/rerank.rs)、`data/rerank.tsv`）: 候補を採るかどうかを、n-gram の Δ だけでなく、助詞の種類・前後の品詞・文法モデルの Δ・共起の差・文書の種類などを特徴量にしたロジスティック回帰で決める。
   - 学習データは、評価に使わない文書に入れた人工誤り（一宮市・高槻市の例規、JEITA モデル契約の大きい方、Wikipedia の 2 本目のダンプ）と、JWTD train の実際の誤字（先頭 5000 件は開発用に除く）。
   - n-gram の Δ が 0 以上の候補をすべて判定器にかける（1 以上に絞ると、変換ミス・助詞の脱落の正解の 3 分の 1 ほどが届かなかった）。
   - 閾値（対数オッズ）は文書の種類ごと（法令文 -1.5 / 一般文 0.0 / 契約書 0.5）。一般文の余計な助詞だけ -1.35 に下げ、名詞の間の「の」を消す候補（「無料のシャトルバス」）は -0.5 にする（`#tau_kind`）。
   - 同音異字には、同じ読みの語どうしの出現数の比・漢字を共有するか、すべての種類に文全体の未出現の並びの割合、名詞の間の「の」か、などを特徴量にしている。
   - 「多くあろう → ある」のような「活用語 + 推量の助動詞」をまとめて直す候補は、JWTD の「〜であろう」の言い換えに引きずられて判定器が強く嫌うので、判定器を通さず種類ごとの閾値で決める（`#exempt inflection-aux`）。
10. **文法モデル**（`data/func.bin`、1.95MB）: 機能語だけ表層形で持ち、内容語を品詞クラスにまとめた 5-gram。単語 3-gram より長い範囲の助詞の並びを見て、判定器の特徴量にする（[scripts/func_vocab.py](scripts/func_vocab.py)）。
11. **誤字パターン**（[src/patterns.rs](src/patterns.rs)、`data/patterns.tsv`）: JWTD train の訂正から集めた書き換え（「をを → を」「れいる → れている」「いづれ → いずれ」など約 3.5 万件、支持数 2 件以上）を照合する（[scripts/patterns/](scripts/patterns/)）。
    - 契約書・法令コーパスで正しい表記として普通に出るもの、送り仮名の揺れは除いている。
    - パターンは文脈を見ないので、「直した文の n-gram の改善幅 + 4 × log10(支持数)」が下限（一般文 3.5 / 法令文・契約書 5）に届くものだけを採る。支持数の多いパターンは文脈が多少不自然でも採り、少ないものは改善幅で確かめる（「いたしまします → いたしまいます」は捨てる）。
    - 重なるパターンはすべて照合し、採れるものの中から選ぶ（支持数の少ない長いパターンが位置を奪わないように）。
12. **カタカナ語**（[src/katakana.rs](src/katakana.rs)、`data/katakana.tsv`）: n-gram はカタカナ語の多くを品詞クラスにまとめるので、中の 1 字の誤りが見えない。コーパスのカタカナ語の出現数の表（8.2 万語、[scripts/katakana_lexicon.py](scripts/katakana_lexicon.py)）を持ち、表にほとんど無い 5 字以上の語を、1 字違い（挿入・置換・入れ替え・語中の削除）でよく使われる語に直す（「オプジェクト → オブジェクト」「キャラクー → キャラクター」）。
    - 固有名詞を短い別の語にする誤検出（「ノアール → アール」）が多かったので、先頭・末尾を消す直し方はしない。表記の揺れ（小書きの仮名・ヴ・末尾の長音）も出さない。
13. **文法の規則**: 判定器では拾いにくい・誤検出しやすい形を規則で扱う。
    - 同じ助詞・接頭辞が 2 つ続く打ち間違い（「土産物はは店」「ごご連絡」）は必ず指摘する。
    - 必ず「に」をとる動詞（基づく・従う・関する・従事する・該当する・違反する など）の直前の「を」は「に」に直す（「資料を基づき」「業務を従事する」）。
    - 名詞の後ろ以外でも、抜けやすい字を補う候補を出す: 引用の「と」（「偽者だ□言う」）、格助詞の後ろの「は」「も」（「江戸時代に□みられない」）、サ変名詞と読点の間の「し」（「普及□、」）、い抜き（「されて□ない」）。
    - 期限の「までに」、文末の命令形（判決主文の「支払え。」）、話し言葉の縮約（「進めてる」の「てる」）、IPADIC が名詞にしている「お忙しい」の後ろへの助詞の補いは候補にしない。
14. **MLM（任意、既定では使わない）**: modernbert-ja-30m で、拮抗する修正案だけを選び直す。
   - 「まで」→「に」を第一案にできる。
   - 一方で、推論時のメモリが 600MB を超える（`--mlm <dir>` で有効）。

## 結果

学習コーパスは次のとおり。

- e-Gov 法令 XML（3.9 億字）
- Wikipedia 日本語版の分割ダンプ 1 本目（4.5 億字）
- 30 自治体の例規集（9,250 万字）
- 官公庁などのモデル契約書・標準約款・契約ガイドライン（約 180 万字、[scripts/contracts](scripts/contracts)）。小さいので 10 倍の重みで数える

評価文（JWTD の test・gold、横浜市市税条例と完全一致する文）は、学習から除いている。

テストに使う文書は、学習にも閾値・判定器の調整にも使っていない。

- 横浜市市税条例（`fixtures/`）
- 学習に入れていない自治体の例規: 加古川市・生駒市（一宮市・高槻市は判定器の学習と調整に使う）
- 契約書: JEITA ソフトウェア開発モデル契約の小さい方（約 12 万字）、IPA アジャイル開発モデル契約（約 6 万字）。JEITA の大きい方は調整に使う
- JWTD v2 test（実際の誤字 5,357 文）。train の先頭 5000 件を調整に使う

人工誤りは種類ごとに 300 文（契約書は 200 文）へ 1 箇所ずつ入れた。誤検出は誤りのない原文での指摘の数。

### 横浜市市税条例

| 誤りの種類 | 検出 | 正しく直せた |
|---|---|---|
| 余計な助詞 | 88.7% | 88.7% |
| 助詞の取り違え | 75.7% | 70.7% |
| 活用の誤り | 74.3% | 72.7% |
| 助詞の脱落 | 72.7% | 69.7% |
| 同音異字の誤変換 | 83.7% | 83.7% |

誤りのない原文に対する誤検出は 14 件（1 万字あたり 0.74 件）。

### 誤検出（1 万字あたり）と検出率の推移

| テスト文書 | 判定器・パターン導入前 | 現在 | 現在の検出（余計な助詞 / 取り違え / 活用 / 脱落 / 同音異字） |
|---|---|---|---|
| 横浜市市税条例 | 1.10 件 | **0.74 件** | 88.7% / 75.7% / 74.3% / 72.7% / 83.7% |
| 加古川市の例規 | 3.08 件 | **1.57 件** | 88.0% / 65.3% / 71.7% / 63.0% / 90.0% |
| 生駒市の例規 | 1.64 件 | **0.93 件** | 89.7% / 71.7% / 73.7% / 67.3% / 90.7% |
| JEITA モデル契約（小） | 3.42 件 | **1.79 件** | 57.5% / 20.5% / 54.5% / 22.5% / 73.5% |
| IPA アジャイル契約 | 3.59 件 | **1.71 件** | 56.5% / 26.5% / 67.5% / 16.0% / 67.5% |

契約書は法令文より言い回しが多様で、取り違えと脱落の検出はまだ低い。判定器は誤検出を減らす方向に効いたが、契約書の検出率は条例より 20〜50 ポイント低い。

PDF から取り出した契約書の本文は文の途中で改行されているので、かな・漢字・数字に挟まれた空白を詰め、文の途中の改行をつないでから測った（[scripts/contracts/reflow.py](scripts/contracts/reflow.py)）。

### JWTD v2 test（実際の誤字 5,357 文）

| 構成 | 検出 | 正しく直せた | 正しい文での誤検出（1 文あたり） |
|---|---|---|---|
| 判定器・パターン導入前 | 19.3% | 15.3% | 6.0% |
| 判定器・文法モデル・パターン | 41.2% | 36.0% | 9.0% |
| **＋カタカナ語・パターン拡充・補う位置の追加（現在）** | **42.3%** | **37.6%** | **9.1%** |

| JWTD の分類 | 件数 | 検出 | 正しく直せた |
|---|---|---|---|
| 脱字（insertion_a） | 1,085 | 67.5% | 62.4% |
| 漢字誤変換（kanji-conversion_a） | 1,782 | 38.2% | 37.1% |
| 余分な文字（deletion） | 1,023 | 38.5% | 31.8% |
| 置き換え（substitution） | 774 | 30.6% | 22.9% |
| 入れ替え（transposition） | 52 | 59.6% | 32.7% |

実際の誤字の検出は倍以上になったが、正しい文での誤検出も 1 文あたり 6.0% → 9.1% に増えている。
最後の改善は、一般文の判定器の閾値を厳しくして誤検出を前の版にそろえた点での比較（閾値を前の版のままにすると検出 44.6%・誤検出 10.4%）。

**どこまで伸ばせるか**: JWTD test の誤りのうち、今の方式で修正候補を作れているのは約 61%（n-gram の候補 48%、誤字パターン 23%）で、これが検出の上限に近い。
候補に入っているのに落としている分は、判定器を緩めれば拾えるが、検出 1 ポイントごとに誤検出もほぼ 1 ポイント増える（閾値を種類ごとに変えても同じ）。
線形の判定器を勾配ブースティング木 (LightGBM) に替えても、同じ誤検出で検出は +1〜1.5 ポイントだった。
頭打ちの原因は判定器ではなく、言語モデルが持つ情報（単語 3-gram・語彙 1 万語）の方にある。
Wikipedia の 1 文だけを渡す評価なので文書内繰り返しの抑制が効かないこと、正しい文での誤検出の約半分は Wikipedia の訂正後の文に残っている本物の誤りであることは、以前と同じ。

増えた検出の多くは誤字パターン（JWTD train 由来）による。パターンは同じデータセットの train から作っているので、Wikipedia 以外の文書では上がり幅が小さい可能性がある。

### 回帰テスト

[tests/regression/cases.tsv](tests/regression/cases.tsv) に、例文と同じ型の誤り（余計な助詞・推量の「あろう」・助詞の取り違えと脱落・打ち間違い）と、誤検出しやすい正しい文（「であろう」「必要があろう」「までに」「無料の」「お忙しいところ」「支払え。」など）を、一般文・契約書・法令文で 223 件置いている。
入力に出た指摘をすべて当てた文が期待どおりになり、直した文にはもう指摘が出ないことを確かめる。playground のサンプル（[playground/web/samples.json](playground/web/samples.json)）も同じテストで確かめる。

検出できていない既知のケースは [tests/regression/known_gaps.tsv](tests/regression/known_gaps.tsv) に置き、失敗にはせず結果を表示する（「豆腐は店」「商家から建物」のような、名詞の間の余計な助詞で n-gram の差が小さいもの）。

### サイズと精度

調整用シードで、誤検出率（1 万字あたり約 0.8 件）をそろえて比べた（判定器を入れる前）。

| 構成 | サイズ | 余計な助詞 | 取り違え | 活用 | 脱落 |
|---|---|---|---|---|---|
| 語彙 28.6 万・4-gram（最初の版） | 542MB | 85.7% | 64.3% | 79.7% | 52.0% |
| 語彙 5 万・4-gram・足切り弱 | 233MB | 84.7% | 63.3% | 80.7% | 43.7% |
| 語彙 1 万・3-gram・足切り中 | 32.6MB | 91.7% | 61.7% | 79.7% | 32.3% |
| **語彙 1 万・3-gram・足切り強（既定）** | **12.7MB** | **93.0%** | **60.3%** | **82.7%** | **36.0%** |
| 存在フィルタのみ・修正案なし（`build-set`） | 3.0MB | 83.0% | 29.0% | 82.3% | 29.3% |

修正案をあきらめて n-gram の有無だけを持つ方式（`build-set`）も試した。精度を支えているのは確率の情報なので、修正案をあきらめてもサイズはほとんど減らなかった。

### 試してやめたこと

- 文字単位の編集（1 文字削除・入れ替え・かな補完）: 35 倍遅くなるわりに伸びが小さい。
- 文法モデルの Δ を n-gram の Δ に直接足す: 伸びが小さい。判定器の特徴量にする方が効いた。
- 文法モデルを大きくする（5.3MB）: 1.95MB 版と同等。
- 誤字パターンを Aho-Corasick で照合: 常駐が 8.5MB 増える。先頭 2 文字の索引で同じ速さになった。
- 判定器を勾配ブースティング木にする: 同じ誤検出で検出 +1〜1.5 ポイントだけ。実装と容量の増加に見合わない。
- n-gram の Δ が大きい候補は判定器によらず採る: JWTD の開発用で正解 6 件に対して正しい文の候補 12 件が通り、割に合わない（代わりに「に」をとる動詞の規則を入れた）。
- 名詞の間の「の」を候補から外す規則: 実際の誤字にも余計な「の」が多かった（開発用 4,883 文で 107 件）ので、判定器の特徴量と別の閾値に替えた。
- enno.jp などの外部サービスの出力から学ぶ（蒸留）: 利用規約で禁止されているのでやらない。パターンを蓄積する方式だけを、公開データ (JWTD) で自前に作った。

## 使い方

```bash
scripts/build_all.sh                                    # 辞書・コーパス取得〜モデル構築 (約 2 時間)
cargo run --release -- check fixtures/yokohama_shizei_jorei.txt
cargo run --release -- eval --sweep --seed 11 --thresholds 0,0,0,0,inf,inf fixtures/yokohama_shizei_jorei.txt  # 閾値の掃引
cargo run --release -- eval-jwtd data/jwtd/test.jsonl
cargo run --release -- bench-cache fixtures/yokohama_shizei_jorei.txt  # 初回 / キャッシュ命中 / 1 文編集
cargo run --release -- prune-tables -o data/dist        # 配布用に活用表・同音異字表を語彙で絞る
cargo test --release --test regression -- --nocapture  # 回帰テスト (data/dist が必要。無ければ飛ばす)
CELSO_TRACE=1 celso check                               # 閾値に届かなかった候補も含めて採点の内訳を表示
```

- 閾値は `--thresholds`（法令文）と `--general-thresholds`（一般文）で指定する。並びは `delete,substitute,inflection,insert,homophone,char` で、log10 の値。`inf` で無効にする。
- `scripts/size_sweep*.sh` と `scripts/set_sweep.sh` は、サイズと精度の比較に使ったスクリプト。

## Playground (WebAssembly)

[playground/](playground/) は、celso をブラウザで動かす crate と静的ページ。GitHub Pages (`gh-pages` ブランチ) で配信している。

- `default-features = false` で celso を使う。Zig コアの代わりに delarocha の純 Rust 実装で分かち書きし、IPADIC の生ファイル (lex.csv / matrix.def / char.def / unk.def) から辞書を作る。MLM は外す。
- モデルは mmap できないので、`Model::from_bytes` / `Cooc::from_bytes` でメモリへ読む。
- 読み込みと検査は Web Worker で行う。データ (gzip で約 30MB) は gzip のまま置き、`DecompressionStream` で展開する。
- サンプル文は `playground/web/samples.json` に置き、期待する修正後の文と一緒に回帰テストで確かめる（`playground/tests/example.rs` は純 Rust の分かち書きで同じことを確かめる）。
- 純 Rust の分かち書きでも、市税条例全文の指摘はネイティブ版と完全に一致する (`playground/tests/example.rs`)。

```bash
scripts/build_playground.sh     # wasm のビルドとデータの gzip (playground/web へ)
python3 -m http.server -d playground/web 8000   # 手元で確認
scripts/deploy_playground.sh    # gh-pages ブランチへ push
```

## 既知の課題

- **契約書の検出率**: 誤検出は 1 万字あたり 1.5〜1.9 件まで減ったが、取り違え・脱落の検出は 14〜28% と低い。契約書コーパスの拡充（経産省・特許庁のモデル契約書は WAF で取得できなかった）が次の一手。
- **一般文の誤検出**: JWTD の正しい文で 1 文あたり 9.1%。これ以上の検出は、誤検出とほぼ 1 対 1 の交換になる。
- **候補に入らない誤り**: JWTD の約 4 割（助詞以外の語の誤り、1 字の漢字の変換ミス、文脈の知識が要る誤りなど）は修正候補すら作れていない。
- **名詞の間の余計な助詞**: 「飲食は店」は拾えるが、「豆腐は店」「商家から建物」のように n-gram の差が小さいものは拾えない（known_gaps.tsv）。
- **漢字誤変換**: 542MB 版より弱い。
- **文字単位の誤字・脱字**: 実装（`char`）はあるが、遅く誤検出も多いので既定では無効。
