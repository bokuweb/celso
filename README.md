# celso

高速な日本語誤字脱字チェッカーの試作。

**修正候補を作り、単語 n-gram 言語モデルで編集前後を比べる**という古典的な手法を、法令文向けに工夫して組み合わせている。
加えて、修正案が拮抗する箇所だけを小さなマスク言語モデル（MLM）で選び直す。
横浜市市税条例（約 20 万字）全体を **0.1〜0.6 秒**で検査できる（8 コアの CPU、GPU 不要）。

```
$ echo "西口側までは宿泊から施設や地元の日本酒や、山の幸を揃えた飲食は店、呑み屋など多くあろう" | celso check
3..5    substitute  「まで」→「に」     Δ=7.58  西口側[まで]は宿泊から…   別案: 「まで」→「」(7.18) 「まで」→「で」(5.18)
8..10   delete      「から」→「」       Δ=7.03  西口側までは宿泊[から]施設…
30..31  delete      「は」→「」         Δ=6.56  …揃えた飲食[は]店、呑み屋…
40..43  inflection  「あろう」→「ある」  Δ=9.46  …呑み屋など多く[あろう]   別案: 「あろう」→「あり」(9.12) 「あろう」→「あっ」(3.32)
4 findings, 44 chars in 135.75ms
```

指摘ごとに第一案と、別案を最大 2 件まで出す。

## なぜこの方式か

例文の誤り（宿泊**から**施設、飲食**は**店、多く**あろう**）は、どれも**単語としては正しく、並び方だけがおかしい**。

- 形態素解析の辞書では「宿泊/から/施設」がすべて既知語として解析できてしまうため、検出できない。
- ruri のような文埋め込みモデルは、文全体の意味をベクトルにまとめる。助詞が 1 つ増えても意味はほとんど変わらないので、埋め込みもほぼ動かない。

並びの不自然さを見るには言語モデルが必要になる。ただし、文全体の尤度をそのまま閾値で切ると、珍しいが正しい文まで拾ってしまう。
そこで「この位置をこう直すと尤度がこれだけ上がる」という**相対比較**で判定する。

## 仕組み

1. **分かち書き**: [delarocha](https://github.com/bokuweb/delarocha)（Zig コア）+ IPADIC。辞書は `celso build-dict` で一度だけバイナリに変換し、起動時に mmap する。
   数字列は `<num>` にまとめる。全角英数は、文字数を変えない NFKC で正規化する。
2. **候補生成**（[src/checker.rs](src/checker.rs)）
   | 種類 | 例 | 内容 | 閾値 |
   |---|---|---|---|
   | delete | 宿泊**から**施設 → 宿泊施設 | 単純な助詞・1 文字の平仮名・重複語を削る | 3.0 |
   | substitute | 西口側**まで**は → 西口側**に**は | 単純な助詞どうしを置き換える | 3.0 |
   | inflection | 多く**あろう** → 多く**ある** | 活用語と後続の助動詞列を、同じ語の別の活用形に置き換える | 2.0 |
   | insert | 市税**□**賦課 → 市税**の**賦課 | 名詞の直後に助詞を補う | 1.5 |
   | homophone | 対**象** → 対**照** | 読みが同じで漢字の違う語に置き換える（かな→漢字や送り仮名違いは表記ゆれなので除外） | 3.0 |
   | char（既定は無効） | きかっけ → きっかけ | 1 文字削除・入れ替え・かな補完を、分かち書きし直して比較する | — |
3. **1 段目（n-gram）**: 編集箇所とその後続 3 語の対数確率（log10）を、編集前後で比べて差 Δ を出す。閾値を超えたものを指摘する。
4. **誤検出の抑制**（精度の大半はここで決まる）
   - **未出現ゲート**: 元の文の編集箇所まわりに、コーパスで一度も見ていない 3-gram がある場合だけ候補を評価する。
   - **文書内の繰り返し**: 指摘箇所の前後 2 文字を含む文字列が、同じ文書に 2 回以上出てくる場合は指摘しない。誤字はたいてい 1 回限りだが、条例特有の言い回しは何十回も出てくる。
   - **箇所へのまとめ**: 1 文字以内で隣り合う候補は同じ誤りの別解として 1 箇所にまとめ、上位 4 案を残す。
5. **2 段目（MLM、修正案選び）**（[src/mlm.rs](src/mlm.rs)）: 指摘が確定した箇所のうち、1 位と 2 位の案の n-gram スコア差が 1.0 未満のものだけを、modernbert-ja-30m で選び直す。
   - **穴埋め採点**: 直す範囲（前後 1 文字を含む）のサブワードをまとめてマスクし、1 回の推論で採点する。同じ長さの置換候補はマスク系列を共有する。
   - 1 文に複数の誤りがあるときは、ほかの箇所を直した文脈でもう一度採点する。
   - n-gram は前後 3 語しか見ないため「西口側[に]は … 多くある」の呼応を捉えられないが、MLM は文全体を見るので「には」を選べる。
6. **言語モデル**（[src/lm.rs](src/lm.rs)）: 4-gram、補間 modified Kneser-Ney。自前実装で、全次数の n-gram を 1 枚のオープンアドレス法ハッシュ表に詰め、キーは 64bit の指紋で持つ。

### MLM を採否の判定にも使わない理由（速度）

MLM を指摘するかどうかの判定にまで使う方式（`--mlm-accept`、`--pll`）も試した。
助詞の取り違えの検出は +8pt、余計な助詞は +3.5pt と上がった（誤検出率は同等）が、市税条例全文で MLM の系列が数千本になり、n-gram だけの数十〜数百倍遅くなった。
既定では、MLM は修正案選びだけに使っている（市税条例全文で 11 系列）。精度は、実行時のコストがかからない学習コーパスの拡充（例規集）で上げている。

## 結果

学習コーパスは 3 種類、合計約 2.3 億トークン。モデルは 1.08GB（n-gram 5,154 万）、構築に約 2 分半かかる。

| コーパス | 規模 |
|---|---|
| e-Gov 法令 XML（全 9,003 法令の最新版） | 3.9 億字 |
| Wikipedia 日本語版（分割ダンプの 1 本目） | 4.5 億字 |
| 30 自治体の例規集 | 9,250 万字 |

### 横浜市市税条例（学習には含めない。他市の例規と完全一致する文も学習から除外）

- **速度**: 206,121 字を **0.13 秒**（n-gram のみ）、**0.3〜0.6 秒**（MLM で修正案選びあり）。モデル読み込みは別に 0.3〜1 秒。
- **誤りのない原文に対する誤検出**: 18 件（1 万字あたり 0.95 件）。うち 3 件は「付則」→「附則」で、法令用語としてはむしろ直すべき指摘。
- **人工誤り**（種類ごとに 300 文へ 1 箇所ずつ誤りを入れる。閾値の調整とは別の乱数シードで測定）

  | 誤りの種類 | 検出 | 正しく直せた | v1 の検出（参考） |
  |---|---|---|---|
  | 余計な助詞（宿泊から施設） | 91.3% | 90.7% | 90.3% |
  | 助詞の取り違え | 70.0% | 48.7% | 71.0% |
  | 活用の誤り | 79.7% | 71.0% | 78.7% |
  | 助詞の脱落 | 49.0% | 31.7% | 43.3% |

  原文での誤検出は、v1 の 28 件から 18 件に減った。

### JWTD v2 test（京大 日本語Wikipedia入力誤りデータセット、実際の誤字 5,357 文）

| カテゴリ | 件数 | 検出 | 正しく直せた |
|---|---|---|---|
| 衍字（insertion_a） | 1,085 | 61.4% | 55.2% |
| 脱字（deletion） | 1,023 | 39.6% | 22.6% |
| 漢字誤変換（kanji-conversion_a） | 1,782 | 28.7% | 26.9% |
| 誤字（substitution） | 774 | 25.6% | 11.5% |
| 全体 | 5,357 | 35.5%（v1: 32.7%） | 26.7%（v1: 25.1%） |

訂正後の正しい文に対する誤検出は 1 文あたり 24.8%（v1: 18.7%）と多い。
閾値を法令文に合わせて下げたことと、1 文だけを渡す評価なので文書内繰り返しの抑制が効かないことが原因。
一般文向けに使う場合は、`--thresholds` で閾値を上げる。

## 使い方

```bash
scripts/build_all.sh                                    # 辞書・コーパス取得〜モデル構築 (約 2 時間)
cargo run --release -- check fixtures/yokohama_shizei_jorei.txt
cargo run --release -- check --mlm none FILE            # n-gram だけ (最速)
cargo run --release -- eval --sweep --thresholds 0,0,0,0,inf,inf fixtures/yokohama_shizei_jorei.txt  # 閾値の掃引
cargo run --release -- eval-jwtd data/jwtd/test.jsonl
cargo test --release -- --include-ignored               # 例文の回帰テスト (モデルが必要)
```

- 閾値は `--thresholds delete,substitute,inflection,insert,homophone,char` の順で指定する（log10、`inf` で無効）。
- `CELSO_DEVICE=metal` を付けると、MLM を Apple GPU で動かす（初回にカーネルのコンパイルで数秒かかる）。

## 既知の課題と次の一手

- **文字単位の誤り（脱字・誤字・転字）が弱い**: 編集のたびに分かち書きし直すので遅い。分かち書きせずに採点できる文字 n-gram モデルの併用が本命。
- **助詞の取り違えは、正しく直せる率が 5 割**: MLM を採否にまで使えば上がるが遅い。量子化や ONNX Runtime などで MLM 自体を高速化できれば、使う範囲を広げられる。
- **モデルサイズ**: 1.08GB。確率を 8bit に量子化し、4-gram の足切りを強めれば、数百 MB まで縮められる見込み。
- **学習ベースへの移行**: JWTD の train（約 70 万ペア）と本ツールの人工誤り生成を合わせて、トークン分類型の誤り検出器（GECToR 型）を学習する。
